# Release and upgrade strategy

Covers the release that follows the feature-composition milestone and the rules for every release
after it. The first-release procedure (`publishing.md`) still applies for the mechanics.

## 1. Versions

| Repository | Previous release | This release | Reason |
| ---------- | ---------------- | ------------ | ------ |
| `web-core-template` | `v0.1.0` | **`v0.2.0`** | New optional feature (`zod`) and strict boolean questions. In 0.x a minor bump carries new features. Additive: with every feature off the output is byte-identical to `v0.1.0` (checked by `tools/compare_release.py`), and projects generated by 0.1.0 upgrade cleanly (tested). |
| `developer-platform` | `v0.2.0` | **`v0.3.0`** | New `zod` option, `devkit upgrade`, release-gated options and offline contract snapshots. The supported template range becomes `>=0.1.0,<0.3.0`. |

**Backward compatibility is kept.** devkit 0.3.0 supports template 0.1.x and 0.2.x. What `devkit` needs
from a template is `app_name` and `app_description`, the options it declares, and the Node major;
all three exist in both lines. The only difference is that `zod` appears in 0.2.0, and each option
declares the release it first appears in (`Option.since`): `--set zod=true` against 0.1.x is refused
up front (Copier would silently ignore it), a pinned 0.1.x release generates normally with the options
it has, and `devkit` also verifies after generation that every requested option was recorded. Both
lines are covered by version-specific contract snapshots (section 6). devkit 0.2.0 continues to work
with 0.1.x and never selects 0.2.0.

## 2. Introducing features without altering existing tags

- Published tags are immutable. A feature is commits on `main`, then a **new tag**; `v0.1.0` is never
  moved, re-tagged or deleted.
- Features default **off**, and the release gate proves the default output is unchanged
  (`compare_release.py <previous tag>` must exit 0).
- The new release reuses the default configuration's lockfile byte for byte; only new
  configurations add lockfiles.
- Order, as in `publishing.md`: template first (CI green, then tag), then the platform, then the
  acceptance test against the published pair. The platform must not be tagged before the template
  release it requires exists.
- A breaking template release (new Node major, renamed or removed question, changed default) bumps
  the minor version in 0.x (the major once stable) and ships with a matching platform change in the
  same release: a new range and a new contract snapshot.

## 3. Safe upgrades of generated projects

```bash
git switch -c chore/template-0.2.1          # optional, but it makes the way back one command
uv run devkit upgrade . --dry-run            # the plan and Copier's preview; writes nothing
uv run devkit upgrade .                      # then the real thing
git diff                                     # review; the command exits 3 and names files if there are conflicts
npm ci && npm run check
```

Guarantees, each covered by a test: the project must be a git root with nothing uncommitted or
untracked, otherwise nothing is touched; the installed release must be a plain tag inside the
supported range and the target a newer, published tag inside it; recorded answers (feature selections)
are kept and features introduced by the new release stay off; your own changes are merged, and where
both sides changed the same lines both are kept between markers (exit code 3) with nothing deleted;
the lockfile matches `package.json` for the project's selection; a failure leaves the committed work
untouched.

## 4. `devkit upgrade`: implemented

It is small because everything it needs already existed: the supported range, source resolution,
strict option parsing, release gating, hermetic Copier settings. It is one module (`upgrade.py`) and
one subcommand, and it adds no new decisions, only enforcement of the range for existing projects.

What it deliberately does **not** do: commit anything, switch a feature off, apply several releases
in sequence, or roll back (the clean-git requirement is the rollback: your work is already
committed). It never deletes: Copier's `cleanup_on_error` is off for updates and conflicts are left
inline.

Residual risks: the answers file is read with a small `key: value` reader (Copier writes only flat
lines), so a hand-edited answers file with unusual YAML would be refused rather than guessed at; and
Copier's own merge still conflicts most in `package.json` and the lockfile, which is why conflicts
are reported prominently.

## 5. Preventing unsupported template versions from being selected

| Situation | Mechanism | Remaining gap |
| --------- | --------- | ------------- |
| New project through `devkit new` | The supported range; only release tags (`vX.Y.Z`) are selectable; outside the range is refused (exit 2). | None. |
| Option the selected release lacks | `Option.since` gate before anything is fetched or written, then an after-generation check that the answer was recorded. | None for a correct registry; the check covers a wrong one. |
| Upgrading an existing project | `devkit upgrade` enforces the range, refuses downgrades, unreleased versions and unpublished targets. | Direct `copier update` still takes the newest tag; documented, and a test records it. |
| Project from an unsupported release | `devkit upgrade` refuses with the reason. | Use a devkit that supports it. |
| New project through raw Copier | `_min_copier_version`; strict boolean answers; documentation. | Raw Copier is outside the guarantees; it cannot know the range. |
| A template release that breaks the contract | The minor-bump rule plus the range plus a contract snapshot per release. | Needs the snapshot to be captured at release time (checklist). |

## 6. The skipped contract tests in platform CI

**Decision: validate compatibility offline in CI, and keep the live comparison as a release gate.**
No credentials are involved anywhere.

| Layer | What it proves | Where it runs | Needs |
| ----- | -------------- | ------------- | ----- |
| **Offline contract snapshots** (`tests/contracts/web-core/<version>.json`, `tests/test_contract_snapshots.py`) | For every supported release, the registry agrees with the release's questions (types, defaults, choices, strictness from 0.2.0, absence before `since`) and Node major; a snapshot exists for the oldest supported release and for each release that introduced an option. | CI and locally, always | Nothing |
| **Live release gate** (`pytest -m integration`) | Each committed snapshot still equals the real template (a tag, or the working tree for the newest unreleased version); old and new releases really generate with the right options. | A developer machine with the template checked out, before tagging | A checkout of the private template |

How a snapshot is made: `tools/capture_contract.py --ref v0.2.0 --write` reads `copier.yml` and
`template/.nvmrc` from the release tag with `git show` (the working tree for an unreleased version).
`--check` verifies a committed snapshot against the template.

Alternatives, and why not:

| Option | Why not (for now) |
| ------ | ----------------- |
| CI checks out the private template with a read token | A stored credential, however narrow, for a check that snapshots make unnecessary; the token would be usable by anyone able to change the workflow. Revisit if both repositories become public (then it needs no secret). |
| The template's CI checks out the platform | The same token problem in the other direction. |
| Make the template publish a contract asset on release | A release-process change and a new artifact to trust; the snapshot is that artifact, reviewed in a pull request. |

Which tests still skip in CI, and why: only the live ones (they need the template checkout). They are
the release gate, not the compatibility protection; that is the offline layer, which no longer skips.
Skipping them in CI is a consequence of not holding credentials, not a weakened check.

## 7. Release checklist

1. **Template.** `uv run pytest` (all configurations, end to end); `compare_release.py v0.1.0` exits 0;
   `refresh_locks.py --check` exits 0; update `CHANGELOG.md` and its heading; commit; push; CI green
   on Python 3.12 and 3.14; annotated tag `v0.2.0`.
2. **Platform.** Bump `version` to 0.3.0 in `pyproject.toml` and `src/devkit/__init__.py`; with
   `../web-core-template` at the `v0.2.0` tag run `tools/capture_contract.py --ref v0.2.0 --write`
   for 0.2.0 (the committed snapshot was taken from the working tree) and review the diff, then
   `uv run pytest` and `uv run pytest -m integration` (the live gate, now including the test that
   needs a release to exist); commit; push; CI green; annotated tag `v0.3.0`.
3. **Acceptance.** `devkit new` with and without `--set zod=true` against the published pair; `npm ci`
   and `npm run check` in both; `devkit upgrade` of a `v0.1.0` project to `v0.2.0`.
4. Nothing in either repository is published or tagged until you approve it.
