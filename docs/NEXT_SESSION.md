Architecture in one paragraph: two repositories with separate version lines. `devkit` (this
repository) generates and upgrades projects from a profile's template and enforces which template
releases it supports (`src/devkit/profiles.py`); the template (`web-core-template`) owns every rule
about a project's content in its `copier.yml`, and offers optional features (`zod` so far) as strict
boolean questions backed by one committed lockfile per distinct npm dependency set. The dependency
is one-way (the platform declares, the template knows nothing of it). Details: `docs/architecture.md`,
`docs/feature-composition.md`; roadmap: `docs/full-stack-plan.md`; releases: `docs/release-strategy.md`.

## 6. Unresolved technical decisions

1. **PyYAML.** `devkit` reads `copier.yml` question names and `.copier-answers.yml` with small regex readers
   instead of a YAML library. Checked at the checkpoint: they agree with a real YAML parser on every real
   file (template v0.1.0 tag, working tree, fixtures) and cannot execute anything, so there is no
   demonstrated problem. Declaring `pyyaml==6.0.3` (already locked through Copier) would be a one-line
   change but needs approval (the platform's rules require it). Decide in a future review.
2. `devkit upgrade` goes to one target release; chaining several is deferred. It cannot switch a feature off.
3. Layering add-on templates (for native iOS) is a hypothesis with no prototype.
4. The lockfile matrix is capped at 16 by a test; beyond that, curated presets.
5. Whether to pin `ubuntu-latest` in both CI workflows (GitHub announced a label migration).
6. Branch protection on both repositories: not created; may need a paid plan for private repositories.

## 8. Publication sequence: template first, platform second

1. Merge the template PR after CI is green and you approve; on updated `main` create the annotated tag
   `v0.2.0` and push it. Tag only a commit CI has passed.
2. Re-capture the platform's 0.2.0 snapshot from that tag (prerequisite 3), bump, commit, push, wait for CI.
3. Merge the platform PR and tag `v0.3.0` on the passing commit.
4. Run the acceptance check against the published pair.

Never move or delete a published tag; fix forward. Mechanics and commands: `docs/publishing.md` and
`docs/release-strategy.md`.
